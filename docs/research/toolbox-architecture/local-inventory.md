# Local architecture inventory for a KiCad toolbox direction

Date: 2026-09-09. Scope: bounded, read-only source inspection, plus creation of this memo. No native tools, model runs, builds, tests, Git operations, refactoring, or deletion were performed. Existing work and evidence are preserved. This is an architecture inventory, not a current-source certification. Other owners have recently changed source; symbols are more durable references than line numbers.

## Finding

The reusable toolbox already exists in substantial part, but its useful generic CAD surface is inside the runner rather than the public EvlEDA MCP server. Three distinct compositions coexist:

1. The older application workflow: `src/mcp/main.ts` constructs `createProductionApplicationService`; `src/mcp/server.ts:createMcpServer` exposes `OPERATION_NAMES` through `ApplicationService.dispatch`. These are fourteen lifecycle/application operations, not the fresh CAD tools. `src/application/factory.ts:createProductionApplicationService` constructs `ReferenceStageContextProvider` and durable application stores. This is the Rev-A reference workflow described by the older product contract.
2. The CAD harness: `src/cli/pcb-agent.ts` composes provider, native sessions, project preparation, compiler artifacts, tools, acceptance, and `src/harness/pcb-agent-harness.ts:runPcbAgentHarness`. Its host-owned tool set lives in `src/harness/kicad-tools.ts`, including incremental schematic authoring and contract-aware PCB operations.
3. The local Flux application: `src/api/server.ts:createLocalApiServer` optionally loads `loadFluxProductionComposition`, then `createFluxRuntime`; `src/flux/runtime.ts:createFluxRuntime` delegates execution to `runPcbAgentCli`. `FluxRunManager` owns the additional project/thread/run, prepare/open/checkpoint/approval/resume lifecycle. `src/cli/flux-control.ts:runFluxControlCli` is a client of that local API, not another CAD engine.

There is no `src/api/services` directory in the inspected tree. The relevant service layers are `src/application` and `src/flux`. A toolbox architecture should start by clarifying these composition boundaries, not by discarding the CAD core or assuming every existing module is needed for every interaction.

## Entrypoints and packaging

`package.json` maps `mcp` to `tsx src/mcp/main.ts`, `pcb-agent` to `tsx src/cli/pcb-agent.ts`, `fluxctl` to `tsx src/cli/flux-control.ts`, and `dev:daemon` to `tsx src/api/main.ts`. The published local bin is `evleda-fluxctl -> dist/src/cli/flux-control.js`. `start` verifies packaged deep-rule resources and runs the API; `dev` starts daemon plus UI.

The build currently includes a hard-coded DOC2 inspection-runtime verification path, CLI-profile evidence verification, both resource checks, TypeScript, resource packaging and packaging tests, and the Vite UI build. That is an application build composition; a separately usable toolbox package could avoid requiring the UI or commissioning workflow to build, while retaining checks for resources/runtime dependencies actually used. No build was run here, so portability is a dependency observation, not a reproduced failure.

`ui/src/route.ts:resolveUiRoute` selects Flux only for `/flux` or `/flux/`; other paths select the commissioning bench. `ui/src/main.tsx` imports both `App` and `FluxDesignerApp`. The API also constructs the legacy `ApplicationService` when Flux is configured. These are concrete coupling points for an optional host split.

The public MCP server advertises read-only/idempotent annotations and delegates validation to the common application dispatcher so REST/MCP errors agree. Preserve that transport consistency when exposing a new tool surface. Replacing its fourteen application operations outright would be a compatibility change; a separate toolbox namespace or entrypoint is easier to evaluate without disturbing existing users.

## Strict runner, distinct from the tools

`runPcbAgentHarness` maintains operations, iteration results, native validation status, source-binding snapshots, and host-only mutation dispositions. Configuration includes an exact compiler-owned provider prompt, mutation allowlist, contract identity, post-schematic readback, full-validation phase boundaries, iteration limit, completion gate, invalidation hook, and source-capture hook. The code therefore already separates several mechanism/policy concerns through interfaces, even though the CLI composes them tightly.

`src/flux/run-manager.ts:FluxRunManager` adds persistent transitions and idempotency, including `prepareRun`, `approvalSubject`, `approveRun`, and `resumeRun`. It rejects uncertain restart states and checks toolchain/open/checkpoint authority. `src/flux/runtime.ts:createFluxRuntime` additionally owns prepared bindings, editor process and IPC bindings, preview manifests, inspector operations, and release uncertainty. These concerns are justified for a durable unattended local application, but a model already operating inside an authorized interactive host may not need a second project/thread/approval workflow for every CAD session.

Candidate simplification is therefore to make the runner and Flux workflow optional clients of the same safe CAD service. It is not to let the model create native-pass evidence or skip persistence verification. Evidence required before simplifying approval/checkpoint machinery: enumerate the precise side effects the current host authorizes, identify what the new host already guarantees, demonstrate stale-session/wrong-board prevention and partial-failure recovery, and retain old persisted run readers. The current user pause is not permission to change this machinery.

## Dormant, optional, and superseded-for-this-direction scope

The older product contract and HANDOFF describe a nine-stage full hardware workflow, including firmware contract, simulation, manufacturing package, bring-up, physical qualification, and release. These are broader than the user's clarified KiCad MCP/skills/design toolbox objective. Their implementation and history remain useful and must be preserved; they are candidates for optional modules or deferred product work, not deletion.

`docs/product-contract.md` explicitly says Phase-A `src/agents` is not composed into the application/factory, REST, MCP, or UI and has no default live provider. A bounded import search found no `agents/` imports in the inspected application/API/MCP/Flux/UI paths. This supports treating the subsystem as dormant in these entrypoints, not proof that every conceivable script never imports it. Its trust/replay, role orchestration, and architecture IR should not be required dependencies of the CAD toolbox merely because they exist.

The older application uses `src/application/application-service.ts:ApplicationService`, `physical-evidence.ts`, `src/integrations/reference-stage-context.ts`, `reference-kicad-backend.ts`, `reference-simulation.ts`, and firmware compiler/target-builder modules. Those support the reference application. Their lifecycle assertions should stay with it. A toolbox can retain the distinction between candidate evidence and a qualified/released board without requiring a bring-up schema to inspect or modify a schematic.

The commissioning bench UI and Flux UI are optional presentations. CLI-controlled Flux is already headless from the user's perspective, but still depends on the Flux server/lifecycle. A thin MCP tool entrypoint would be a genuinely different composition, not simply another alias for `fluxctl`.

## Overlap worth investigating, not automatically removing

1. **KiCad parsers.** `fresh-kicad-parser.ts:parseDocument` is a bounded source-span/quoted-atom parser feeding PCB, schematic, presentation, terminal geometry, and netlist readers. `kicad-library-resolver.ts:BoundedSExpressionParser` separately reads stock library content; `fresh-clearance-evidence.ts:BoundedSExpressionParser` reads rule/PCB sources; `pcb-practice-analyzer.ts:parseSExpressionDocument` has its own parse tree; `reference-simulation.ts:parseSExpression` is another reader. Common syntax mechanics are plausible consolidation targets. Their semantic projections, source-span needs, budgets, version coverage, and unsupported cases differ. First compare quoted/private-field handling, duplicate preservation, physical pads, malformed input, and limits across a shared corpus. Do not replace all with a permissive parser or count their existence as waste.
2. **Receipt/state layers.** Application bundle replay, the Phase-A agent replay store, compiler bundle storage, Flux open/checkpoint/approval receipts, harness operations/source bindings, native report identities, and schematic batch receipts describe different events. Shared identity/serialization/validation helpers may simplify maintenance; collapsing the events into a single vague 'validated' receipt would destroy meaning. Map producer, consumer, authority, persistence/restart behavior, and version compatibility first.
3. **Control paths.** Legacy REST/MCP share `ApplicationService.dispatch`; Flux REST and CLI share the Flux client/run-manager path; the CAD CLI calls the harness directly. The main opportunity is one reusable CAD execution service and several hosts. It is not necessary to force both the legacy application and Flux through one new lifecycle immediately.
4. **Acceptance profiles.** `fresh-acceptance.ts:evaluateLedIndicatorAcceptance` and `fresh-deep-rules.ts` contain explicit LED compatibility policy; `fresh-design-acceptance.ts` and the compiler supply generic policy. Keep legacy proof readers and fixtures, but avoid using the LED path as the template for each new board family. New generic capabilities need reusable geometry/connectivity support, not another hardcoded example contract.
5. **Server/UI projections.** `src/flux/deep-rule-summary.ts` and `ui/src/flux/deep-rule-summary.ts`, plus public projection/contract presentation modules, warrant a contract comparison. Similar names alone do not prove duplicated validation: public display and authoritative server parsing have different trust roles.

## Actual gaps and evidence freshness

The public MCP composition gap is directly established by source: no fresh CAD tool registration occurs in `src/mcp/server.ts`. The current CLI/Flux architecture also ties many operations to a compiled contract, fresh-project lifecycle, and host-owned native session. Designing a direct toolbox API requires deciding which read tools are standalone, which mutations need a session/checkpoint, and which contract compounds require a bound specification.

The dated `docs/current-status-and-roadmap.md` reports a successful attempt-15 divider: seven iterations, 44 mandatory checks, zero ERC/DRC/unconnected counts, native ink coverage, and an independent visual review. It explicitly limits this to one fixed demonstration and documents long VOUT routing, weak compactness, missing connector-function silkscreen, remaining power/return-path/USB/impedance/electrical-sizing work, and no full RP2350 proof. These are reported historical evidence; this inventory did not open or rerun the absolute D: proof artifacts.

Current source is ahead of some roadmap wording. `kicad-tools.ts` imports and calls terminal grouping, source adapter, work-budget, schematic batch, and physical-pad observation modules. Its `#physicalPadState` calls `collectKicadNativePadObservation`; `src/cli/pcb-agent.ts` derives an approved physical-footprint resolver and passes it to tool construction. Therefore 'not wired at all' would be wrong. Conversely, that wiring does not prove integrated native operation. The roadmap's historical DOC2/profile-12 proof and separately installed DOC3/offline checks cannot certify these later source changes. Fresh source review and targeted integration evidence are required before changing any capability claim.

`fresh-schematic-work-budget.ts` currently declares a 20,000,000-unit deterministic aggregate budget with `complete`/`exhausted` outcomes. This is not a KiCad size limit or a measured performance guarantee. The roadmap's older 8-component/64-endpoint diagnosis should be treated as historical context until current admission and host consumption are traced end to end. This inventory does not claim a current native capacity ceiling.

The first-class application invocation ledger remains a documented W-08 gap: `ToolInvocationRecord`/`state.invocations` are reserved, and embedded native reports do not constitute that ledger. Before implementing it for a toolbox, decide whether a concise session operation record supplies the required audit function. Do not finish a broader application's reserved schema merely because it exists.

## Architecture options for synthesis

**Existing strict application:** retain the current routes and lifecycle as the main user interface. It already centralizes approvals, restart handling, source-bound checks, and result history. It also leaves the user operating two layers of agent/task orchestration and keeps the MCP surface distant from actual CAD primitives. Choosing this requires a reason that those workflows are the primary product.

**Thin model-driven toolbox:** expose reusable reads, bounded mutations, library lookup, guidance retrieval, render inspection, and native checks directly to the authorized host. Preserve session safety and explicit unsupported outcomes. Let the host plan and decide when to invoke analyses. This best matches the clarified interaction direction, but loses nothing only if extraction retains save/rollback/source semantics and reports incomplete validation honestly. The present code does not yet supply this standalone public composition.

**Hybrid with optional strict runner:** define a common safe CAD service and expose it through MCP; keep the existing harness/CLI and Flux lifecycle as optional clients and evaluation paths. This preserves the most existing investment while allowing interactive model-led work. It is an architectural recommendation for consideration, not an implemented split. A first reviewable experiment should be a narrow read-only toolbox composition and contract map, followed by one isolated reversible mutation path when separately authorized. Measure user task completion, correction effort, round trips, failure recovery, and retained checks on representative tasks. Code size and test totals are not waste metrics; no savings percentage, ETA, or model-performance claim is supported by this inventory.
