## Standalone guidance

Run `pnpm mcp:toolbox` as a stdio MCP server. This entrypoint currently serves verified research guidance; it does **not** open KiCad, choose a project, create a native session, or enable edits. Its status reports `guidance-only` explicitly.

Available operations:

- `evleda_toolbox_status`: current capability and recovery state.
- `evleda_rule_topics`: the 17 research dossiers and catalog metadata.
- `evleda_find_rules`: complete rule records selected by topic, tag, ID, category or severity, with explicit pagination.
- `evleda_read_guide`: a complete guide by exact topic, slug or dossier number.
- Seventeen `evleda://guides/...` resources expose the same full dossiers.

The 1,773 records are research guidance, not 1,773 completed or executable checks. The existing verified resource loader supplies them; no alternate corpus or source path can be chosen through a model argument.

The packaged workflow skill is [skills/evleda-pcb/SKILL.md](../skills/evleda-pcb/SKILL.md). It is not automatically installed into global user settings.

## Host-bound CAD composition

`createKicadToolboxMcpServer({ cad, access, compoundContractIdentity? })` in `src/mcp/toolbox-server.ts` accepts already-bound host capabilities. It does not deserialize authority, executables or project selection from MCP requests. The host may expose read-only access or explicitly enable editing; clients cannot promote access through a tool call.

`openKicadToolboxSession` in `src/mcp/toolbox-session.ts` composes an existing manifest/socket-bound authority with a prepared isolated **copied project**, exact active-board verification and the existing persistence fingerprint callbacks. It returns the CAD tools, a current-document assertion, a source fingerprint function and an awaited close operation, without creating a model/provider or entering ApplicationService/FluxRunManager. The server checks the active document before CAD operations and again after edits/checks; status distinguishes a supplied binding from a currently available document.

Preparation, runtime/profile selection, editor opening and fresh-project authority belong to the owning host. The copied helper does not authorize generic fresh projects from plain data. The separate fresh preparation/session path constructs and checks the existing fresh capabilities, then supplies the exact derived connectivity-contract identity to the same server factory.

## Native copied-project command

`pnpm mcp:toolbox:native --help` describes the separate native stdio entrypoint. Unlike `mcp:toolbox`, it opens a real KiCad editor and connects the existing tools. Required host arguments are `--profile`, `--profile-sha256`, `--profile-bytes`, `--project-dir`, `--output-dir`, and `--board`. The board selector is a filename in the source project's root. Output must be an empty directory, or an existing matching copied-project preparation when `--resume` is supplied.

The pinned local JSON profile supplies the established `kicadToolchain` and `kicadMcpRuntime` sections. An existing Flux profile may be reused, but its provider, compiler, credentials, and UI configuration are not interpreted or initialized. The profile/runtime/library formats are not replaced by a second configuration framework. Native startup reuses the existing runtime verification, exact executable binding, editor launch and session code. Only `SYSTEMROOT` and `WINDIR` are passed from the host environment; the existing runtime/editor code supplies its private paths.

CAD tools are read-only by default. Add `--edit` in the **host command configuration** to expose reviewed edits; a model tool call cannot enable them. Required profile pins remain explicit; the command does not silently trust any runtime located on PATH.

Before opening the editor, the resolved copy must stay within output and separate from the source, with no source aliases, nested links or shared hardlinks. Startup repeats that check immediately before launch. Use `evleda_finish_session` before disconnecting: it drains an active operation, requests normal closure of the exact owned editor, waits for actual exit, closes the sidecar and releases its private socket. Fresh checkpoints are published only after confirmed teardown. Closing stdin or sending a handled termination signal also attempts this lifecycle, but an impatient client can kill a host before cleanup finishes; an explicit finish call gives it time to return confirmation. Uncertain state is retained and reported.

`scripts/smoke-toolbox-native.ts` uses the same startup with an in-process MCP client. On an isolated test copy, `--edit` temporarily moves the first footprint by 0.25 mm, verifies its saved placement, restores it, collects native checks, and writes `native-toolbox-smoke.json` in output. This is an integration test, not a board-quality or routing test.

## Fresh design startup

The same native command accepts `--new-project <name> --intent <draft.json> --prompt <original-request>` instead of `--board`. In this mode, `--project-dir` is the separate input folder containing the intent file; `--output-dir` must be empty. The routed workflow follows `evleda.pcb-design-intent-draft.v1`, including exact components/pins, electrical inputs, net classes, placement constraints and required 45-degree routing policy. The direct native path also recognizes the explicit V2 plane family described below. Unknowns must remain explicit; the compiler returns questions/issues rather than filling them with defaults.

To resume, use the same output, name and approved host profile with `--new-project <name> --resume`, omitting `--intent` and `--prompt`. The persisted canonical bundle remains authoritative. Resume checks its reference, report/checkpoint relationship, current sources, unsafe-terminal state, native toolchain and net-class semantics before minting a new capability. Authored resumes do not use blank-project Open normalization. Changed sources/checkpoints are errors, not an invitation to reconstruct or silently repair authority.

The pinned profile must additionally supply the existing `libraries` and `deepRules` sections. Approved stock library roots must match the pinned installation actually used by the sidecar. The native runtime must supply the private physical-pad and current authoring capabilities; the copied-project DOC2 smoke does not establish those newer capabilities.

Fresh startup compiles the intent with real stock-library inspection and verified guidance, creates the authenticated compilation bundle, prepares native files, materializes and reads back net classes, records a truthful preparation report, and checkpoints before opening KiCad. After Open, it checks normalization against the original captured source authority, rechecks net classes, and resumes the verified project capability before enabling tools. It reuses the CLI's source-bound native schematic render/style and netlist collectors without creating a provider or entering the old runner.

`evleda_design_context` returns the bound contract, execution guidance, acceptance rows and original request so the connected model can author the project through incremental tools. These are requirements, not completion evidence. Source/physical-library checks, save/readback, and recovery requirements remain active. Starting a project does not itself author or route it.

`scripts/smoke-toolbox-fresh.ts` is a deliberately limited three-component integration fixture: native preparation, incremental schematic authoring and PCB synchronization. Its artifact must not be interpreted as a completed routed board. Fresh startup still needs a chat-client deployment test and broader completed-board qualification before broad completion claims.

The direct server projects only tools that the existing bound tool port advertises and its executor supports. Private source/snapshot/commit operations, project rebinding, and raw internal save/check methods are not exposed. Existing copied-project schematic plan and legacy synchronization descriptors are excluded because the existing executor's supported-name set does not admit them. Do not expand only the public descriptor without implementing and verifying the backend path.

### Saved native endpoint connectivity

`evleda_check_endpoint_connectivity` is a public read-only tool for a bound V2 plane-family session. Call it with `{}` after mutations have settled and saved. It accepts no model-provided paths, endpoint IDs or PAD requests; the host derives every endpoint from the authenticated contract and approved physical library. The queued collector checks saved/live source, marker, project scope and library identities before and after native observation, and refuses pending, unsaved or uncertain mutations.

The response contains `sourceBefore`, `sourceAfter`, `sourceUnchanged`, `report`, `diagnostic` and `recoveryRequired`. The public report schema is `evleda.toolbox-endpoint-connectivity.v1` with `assessmentSchemaVersion: evleda.fresh-plane-connectivity.v1`. It retains per-net status/reasons, logical endpoint reachability, eligible physical members, observed components and source/bundle/assessment identities. Distinguish `connected`, `disconnected`, `needs-review`, `unsupported` and `invalid-evidence`; split physical members do not acquire invented component-internal ties.

The full [assessment](../src/harness/fresh-plane-connectivity.ts), including native request envelopes and document paths, is written as a separate immutable host-private artifact. The [public projection](../src/mcp/toolbox-endpoint-connectivity.ts) returns only its filename and content identity in `diagnostic`, not an arbitrary file reader or native request capability. The raw artifact hash and canonical assessment identity are different identities.

This report establishes bounded native physical-pad reachability only. It does not establish intended-plane contact, fresh fill, single-plane-component/island policy, thermal applicability or resolved spokes, absence of cross-net shorts, HF/impedance behavior or ampacity. It reports `verificationPlanRowsPassed: []`, `acceptanceEvaluated: false` and `fabricationAuthorized: false`. Collect separate current native checks and applicable plane/reference evidence.

### Source-bound plane acceptance facts

When advertised, `evleda_check_plane_acceptance` accepts only `{}` for the saved, host-bound V2 project. It accepts no paths, selectors, replacement rules or caller-supplied evidence. Plane-dependent facts require a **current-session fill witness** created only after `fresh_apply_contract_plane` completes its validated native refill and mandatory save/readback. After relevant edits or reopening, reapply and save the bound plane before relying on those facts. Saved fill polygons, an old checkpoint or a serialized diagnostic cannot recreate that witness.
